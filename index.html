Public source · proof of concept · data forwarding validated · not field-integrated
File2TCP ↗
Later transport experiment aimed at replacing the unreliable live UDP handoff with an order-preserving input path. In the original HimawariCast tests, the observed contrast was clear: TSDuck → UDP → himawari-rx produced packet loss / reordering symptoms, while TSDuck → packet-dump file → himawari-rx --file processed the same type of stream normally. File2TCP therefore kept the working file-style output path, but replaced disk replay with a named FIFO plus TCP transport so the byte stream could remain ordered while becoming streamable.
Local source files are dated 2024-06-05. The architecture was: TSDuck → named FIFO → C sender → TCP → modified himawari-rx input stack. The rationale came directly from the behavior documented in himawari-rx issue #2 ↗: UDP input was the failing path; file input was the working path, so the design goal was simply to feed the decoder through an ordered transport. A separate 2021 GK-2A/GNU Radio study had already produced the same transport-level pattern: the UDP-coupled receiver path failed, while native device access and an RSP_TCP-based path succeeded. Taken together, these experiments motivated an ordered-transport alternative for the specific receiver implementations under test. They do not imply UDP is inherently unsuitable: an application that reconstructs packet order and validates its own data stream can be robust to out-of-order UDP delivery. Those experiments alone did not establish whether loss, reordering, or downstream handling was responsible for each failure. Because TCP is a byte stream rather than a datagram API, himawari-rx would need a small input-layer change to read the same length-framed packet stream that its --file mode already parses. The FIFO→TCP forwarding code was tested and data forwarding worked, but the modified himawari-rx input path and end-to-end satellite reception test were never completed after the original receiving environment was no longer available.

RESILIENCE · LOCAL TIME
Monitoring & unattended operation
Operational tool · public source with documented 2023 field history
goesrecv-lock-monitor ↗
Headless reception-health / signal-lock service built around goesrecv decoder telemetry: tracks degradation and recovery, maintains event history, exposes a JSON HTTP API, and can send e-mail alerts for unattended satellite reception.
Originally developed and operationally used in 2023.05–06 for the rooftop GK-2A receiver, where wind or accidental contact could shift the antenna and cause long unnoticed gaps in weather imagery. Controlled antenna-offset tests showed that large Viterbi disagreement could still coexist with normal reception while Reed-Solomon corrections remained zero; once reed_solomon_errors became non-zero, reception was usually already near the FEC cliff. The historical monitor therefore used a stricter RS == 0 operational-health threshold rather than merely mirroring goesrecv's ok flag. The 2026 public hardening retained that criterion while adding dwell-time / hysteresis, alert cooldown, safer credential handling, exact nanomsg framing and a systemd service example.
